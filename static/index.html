Keys

CipherDrop has two sending modes that use ML-KEM-512 differently. Here's exactly what each one does.

Quick Link — encapsulation key (ek)
800 bytes · generated fresh for every file · discarded immediately after use, never transmitted anywhere
Quick Link — decapsulation key (dk)
1632 bytes · lives only in the shared link's URL fragment (after the "#") · browsers never send this to any server
Vault — encapsulation key (ek)
800 bytes · generated once per device, published to this server's identity directory under your chosen Vault ID · genuinely public, meant to be seen
Vault — decapsulation key (dk)
1632 bytes · generated once, stored only on your device (optionally passphrase-protected) · never appears in any link, ever
Session key (either mode)
32 bytes · derived once via ML-KEM-512 encapsulation · used for that single file's AES-256-GCM encryption, then gone

Quick Link doesn't defend against harvest-now-decrypt-later — the link itself is a bearer secret, so intercepting it works whether or not the attacker ever gets a quantum computer. Vault mode does: a real public key travels over real network traffic, and ML-KEM's underlying lattice problem has no known efficient quantum attack, unlike the RSA/ECDH math a classical "harvest now" attacker is actually betting on. Use Vault mode when this specific threat matters to you.

Registering a Vault ID doesn't cryptographically prove you own it — anyone can claim an unused name. Real proof-of-possession would require this server to run ML-KEM operations itself, which would break the "zero cryptographic code on the backend" property everything else here relies on, so that trade wasn't made. Instead, every Vault key has a fingerprint (shown in Settings, and shown to a sender before they encrypt) — the same out-of-band verification model Signal and PGP use. It won't stop a name being squatted, but it makes an impersonation attempt detectable instead of invisible.
